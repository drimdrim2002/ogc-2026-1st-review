제거 실험(ablation)은 해법에서 부품 하나를 빼고 같은 조건으로 다시 돌려, 그 부품이 얼마나 기여하는지 재는 실험입니다. 보고서는 세 가지 설정을 비교합니다.

  • P7에서만 한 팀에 5.8% 뒤졌습니다. 그 문제에서도 39개 팀 중 2위입니다.
  • 참가 팀 전체와 비교하면 차이가 더 큽니다. 다른 팀의 중앙값보다 20~40% 낮습니다.

1장의 채점 방식에 넣어 보면

1장에서 본 대로 순위는 값의 합이 아니라 문제별 등수 점수 R − nb의 합으로 매깁니다. R은 평가된 팀 수, nb는 나보다 좋은 값을 낸 팀 수입니다. 위 배열에 이 식을 그대로 적용하면 이렇습니다.

tishii24 = 39 × 7 + 38 = 311점  (만점 39 × 8 = 312점)

같은 방식으로 나머지 팀도 계산하면 둘째 행이 297점, 셋째 행이 284점이고, 배열의 39행은 이 점수가 높은 순서대로 놓여 있습니다. 이 채점 방식에서는 한 문제를 크게 이기는 것보다 모든 문제에서 고르게 앞서는 것이 중요합니다. 12.5% 앞선 P1도, 1.1% 앞선 P2도 똑같이 39점입니다. 무효한 해 하나는 −1점이므로 그 한 문제에서 40점을 잃습니다. 이 해법이 유효성 재검증과 시간 여유에 공을 들인 이유입니다.

최종 순위는 이 자동 채점에 보고서와 발표 평가를 더해 정해졌습니다. README가 연결한 기사에 따르면 대회에는 55개국 958개 팀 1,448명이 참가했고, 1인 팀 tishii24가 94점으로 1위, 2위가 90점, 3위가 86점이었습니다. 시상식은 2026년 9월 18일에 열렸습니다.

311점은 제가 스크립트의 수치로 계산한 값이고 공식 점수표가 아닙니다. 94점이 어떻게 구성되는지, 본선 8문제의 베이 수·블록 수·제한 시간은 저장소에서 확인하지 못했습니다. P7에서 왜 뒤졌는지도 자료에 없습니다. 기사: 동아일보 2026-09-21, README의 news 링크.

기본 호라이즌 크기가 20이므로 이 문제는 ⌈600 / 20⌉ = 30개 호라이즌으로 풀립니다. 이 스크립트는 최종 발표를 준비하던 9월 15일 커밋에서 추가됐습니다.

이 600블록 문제를 실제로 돌린 결과(값, 소요 시간)는 저장소와 발표 자료에 없습니다. 확장성은 설계상의 근거와 문제 생성기까지만 확인됩니다. 선호 점수 목록을 그대로 두 번 이으면 합이 200이 되는데, 이 점이 결과에 주는 영향도 확인하지 못했습니다.

상대 점수

버전끼리 비교할 때 쓰는 기본 지표는 상대 점수입니다. 문제마다 "비교 대상 중 가장 좋은 값 ÷ 이 버전의 값"을 구해 더합니다(tools/stats.py:297). 그 문제에서 가장 좋았으면 1, 값이 두 배면 0.5입니다. 1부에서 봤듯이 목적 함수 값은 문제마다 수만 배씩 차이가 나므로, 값을 그대로 더하면 큰 문제 몇 개만 보게 됩니다. 비율로 바꾸면 모든 문제가 같은 무게를 갖습니다. 대회의 등수 점수가 문제마다 같은 무게를 주는 것과 방향이 같습니다.

단계별 파라미터 탐색

tune_params.py는 설정 파일의 steps를 위에서부터 차례로 실행합니다. 한 단계 안에서는 후보마다 파라미터 파일을 만들어 문제 묶음을 돌리고, 상대 점수가 가장 높은 후보를 고릅니다. 그 후보의 값이 고정된 채로 다음 단계로 넘어갑니다(tools/tune_params.py:275). 아래는 스크립트가 읽는 키에 맞춰 제가 만든 예시입니다. 저장소에 예시 설정 파일은 없습니다.

# 형식을 보여 주는 예시 (값은 임의)
name: recon-ratio
version: "122"
base_params: params/default.yaml
suite: suites/half.json
timelimit: 60
steps:
  - name: 큰 재구성의 비율
    mode: product                                   # 나열한 값들의 모든 조합
    parameters:
      neighbor.probabilities.large_reconstruct: [0.1, 0.2, 0.4]
  - name: 제거 개수                                 # 앞 단계에서 이긴 값을 고정한 채로
    mode: combinations                              # 직접 적은 조합만
    parameters:
      - { neighbor.reconstruct.remove_count.range: [5, 10] }
      - { neighbor.reconstruct.remove_count.range: [7, 13] }

--cloud를 붙이면 후보 평가가 Cloud Run으로 갑니다. tools/cloud/config.yaml의 현재 설정은 작업 20개, 작업당 CPU 4개와 메모리 8GB, 제한 30분입니다. 문제 묶음을 작업들에 돌아가며 나눠 주고, 작업마다 솔버가 워커 4개를 씁니다. 40문제를 300초씩 한 대에서 돌리면 200분인데, 작업 20개로 나누면 작업당 두 문제, 10분 남짓입니다(이 계산은 설정값으로 제가 한 것입니다).

이 도구들이 대회 중에 실제로 어떤 탐색에 몇 번 쓰였는지는 결과 폴더(tuning/, log/)가 저장소에 없어 확인하지 못했습니다. git 기록에는 "tune-params"(7월 19일), "082: add cloud runner"(7월 31일), "100: add --cloud to tune_params.py"(8월 7일) 같은 커밋이 있습니다.

제출물

제출물은 파일 세 개입니다. 리눅스용 실행 파일 solver, 파이썬 진입점 myalgorithm.py, 그리고 params.yaml입니다. 실행 시 myalgorithm.py가 같은 폴더의 solver를 띄우고 문제를 표준 입력으로 넘깁니다.

  • 채점 환경에 맞춘 빌드: 저자의 기기는 Apple Silicon 맥이고 채점 환경은 리눅스입니다. Dockerfile이 Ubuntu 24.04(x86_64)에 Rust, Python 3.12, Shapely 2.1.2를 깔고, 그 안에서 composer.py --platform linux를 실행해 제출물을 만듭니다.
  • 릴리스 설정: Cargo.toml의 릴리스 프로필은 lto = "fat", codegen-units = 1, panic = "abort"입니다. 의존 패키지는 일곱 개(clap, geo, rayon, serde, serde_json, serde_yaml, rand_pcg)입니다.
  • 개발용 빌드와 제출용 빌드의 차이: local 기능을 켜고 빌드하면 충돌 격자 계산이 예외 경로로 빠질 때 프로그램이 멈춥니다(src/solver/collision.rs:408). 제출용 빌드는 같은 상황에서 기록만 남기고 계속 갑니다. 개발 중에는 문제를 바로 드러내고, 본선에서는 어떻게든 해를 내게 한 것입니다.
  • 시간 여유: 파이썬 쪽이 검증에 2초, 반환에 1초를 떼고(tools/myalgorithm.py:17) 솔버에 나머지를 줍니다. 솔버는 그중 2초를 다시 남기고 끝냅니다(solve_time_buffer_seconds). 자세한 흐름은 6장에서 다룹니다.

build.txt, Dockerfile, tools/composer.py, tools/README.md의 "DockerでLinux向け提出物を作る" 절입니다. 예선 발표 13쪽에서 저자는 후보 해를 여러 번 내보내고 파이썬에서 검증하는 구조를 "숨겨진 문제에서의 예상 못 한 실패에 대비한 안전장치"라고 설명합니다.

AI 코딩 에이전트의 사용

보고서의 "AI Use Declaration"은 세 문장입니다. 저자가 구상한 알고리즘을 구현하는 데 주로 Codex(GPT 5.6 Sol High)를 보조로 썼고, 보고서는 기존 구현을 정리하고 초안을 만드는 데 썼으며, 알고리즘의 아이디어와 설계 결정은 저자가 했고 생성된 코드와 글을 저자가 검토·검증·수정했다는 내용입니다.

저장소 루트의 AGENTS.md가 에이전트에게 준 작업 규칙입니다. 원문은 일본어이고 옮기면 이렇습니다.

  • 기본적으로 서브에이전트에게 맡기지 말 것
  • 과한 주석은 필요 없음
  • YAGNI를 중시하고, 불필요한 보조 함수를 늘리지 말 것
  • 폴백 구현, 하위 호환, 파라미터에 대한 에러 처리는 필요 없음
  • 알고리즘의 동작을 좌우하는 파라미터는 src/params.rs와 params/default.yaml에 추가할 것
  • 지시한 경우가 아니면 테스트를 추가하지 말 것
  • cargo fmt && cargo check --all-features 외의 동작 검증은 필요 없음. train/의 입력으로 돌려 보는 것도 필요 없음
  • 난수열이 바뀌어도 괜찮음

규칙의 방향은 한결같습니다. 코드를 작게 유지하고, 실험용 숫자는 반드시 파라미터 파일로 빼라는 것입니다. 성능 평가는 에이전트에게 시키지 않습니다. 평가는 앞 절의 도구로 문제 묶음 전체에 대해 따로 하기 때문으로 보입니다. 결과적으로 솔버는 src/ 아래 Rust 파일을 모두 합쳐 6,042줄이고(직접 셈), 4부에서 본 것처럼 통하지 않은 시도는 코드에서 지워졌습니다.

git 기록은 2026년 6월 17일부터 10월 9일까지 407개 커밋입니다. 그중 184개가 "005"부터 "123"까지의 번호로 시작하는데, runner.py와 stats.py가 버전 이름으로 결과를 구분하는 것과 맞물립니다. 에이전트가 코드의 어느 부분을 얼마나 썼는지는 커밋에서 구분할 수 없습니다. "평가는 따로 하기 때문"이라는 설명은 규칙과 도구를 보고 제가 한 해석입니다.
