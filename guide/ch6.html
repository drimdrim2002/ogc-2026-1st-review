롤링 호라이즌: 스무 개씩 넣고, 넣을 때마다 전체를 다시 고친다

2장에서 본 2단계의 뼈대는 반복문 하나였습니다. 투입 순서대로 블록을 20개쯤 추가하고(확장), 지금까지 들어온 블록 전체를 SA로 고치고, 다시 20개를 추가합니다. 이 장은 그 반복문 optimize()를 줄 단위로 따라가고, 마지막에 해가 솔버 밖으로 나가 대회에 제출되기까지를 봅니다.

다섯 부분입니다. 1부는 호라이즌이 실제로 어떻게 잘리고 시간이 얼마나 돌아가는지를 숫자로 봅니다. 2부는 호라이즌 하나 안에서 일어나는 일(마감 계산, 확장, SA 호출)입니다. 3부는 w₂를 언제 켜는지, 4부는 후보 해 출력과 파이썬 쪽 검증, 5부는 저자의 보고서와 코드가 다른 부분입니다.

이 장의 수치에 대해

이 기기에는 Rust 툴체인이 없어 솔버를 실행하지 못했습니다. 그래서 시간 수치는 모두 params/default.yaml의 값과 코드의 식으로 계산한 명목 값입니다. 확장이 몇 번 시도되는지, 후보가 실제로 몇 번 출력되는지 같은 실행 결과는 싣지 못했습니다.

// src/solver/optimize.rs:250
fn build_horizons(order: &[usize], base_horizon_size: usize) -> Vec<Range<usize>> {
    let horizon_count = order.len().div_ceil(base_horizon_size);          // ⌈N / 20⌉
    (0..horizon_count)
        .map(|index| order.len() * index / horizon_count                   // ⌊N·i / 개수⌋ 부터
                  .. order.len() * (index + 1) / horizon_count)            // ⌊N·(i+1) / 개수⌋ 앞까지
        .collect()
}
  • 호라이즌은 투입 순서의 구간입니다. order는 블록 번호를 투입 순서대로 늘어놓은 배열이고(2장), 호라이즌 하나는 그 배열의 연속된 구간 시작..끝입니다. N = 250이면 첫 호라이즌은 order[0..19], 둘째는 order[19..38]입니다.
  • 구간의 끝이 곧 누적 블록 수입니다. 코드에서 horizon.end가 "이 호라이즌이 끝났을 때 들어와 있는 블록 수"이고, 뒤에서 시간 배분의 가중치로 쓰입니다.
  • 20은 크기의 상한입니다. 20개씩 자르고 남는 것을 마지막에 몰지 않고, 개수를 먼저 ⌈N / 20⌉으로 정한 뒤 고르게 나눕니다. 그래서 N = 150이면 20개짜리 7개와 10개짜리 1개가 아니라 18~19개짜리 8개가 됩니다.

표는 train/의 14개 파일에서 블록 수를 읽어 위 식으로 직접 계산했습니다. 마지막 열은 (마지막 누적 블록 수)² ÷ Σ(누적 블록 수)²입니다. 각 호라이즌에 실제로 어떤 블록이 들어가는지는 추상 사전최적화의 결과가 있어야 알 수 있어서 계산하지 못했습니다.

2부 · 호라이즌 하나 안에서 일어나는 일

한 호라이즌의 시간 구성

호라이즌 하나에서 코드가 하는 일은 순서대로 넷입니다. ① 이번 호라이즌의 w₂와 마감을 계산한다. ② 워커마다 새 블록들을 자기 해에 끼워 넣는다(확장). ③ 워커들의 해를 SA에 넘겨 마감까지 고친다. ④ SA가 돌려준 워커별 해를 다음 호라이즌으로 넘긴다.

마감은 호라이즌이 시작될 때마다 다시 계산한다

// src/solver/optimize.rs:443
let now = timer.elapsed_seconds();
let remaining_weight: f64 = horizons[horizon_index..]                      // 이번 것을 포함해 남은 호라이즌들
    .iter()
    .map(|remaining| (remaining.end as f64).powf(phase_params.time_allocation_power))
    .sum();
let current_weight = (horizon.end as f64).powf(phase_params.time_allocation_power);
let horizon_deadline = now + (deadline - now).max(0.0) * current_weight / remaining_weight;

호라이즌의 가중치는 (누적 블록 수)γ이고 γ는 time_allocation_power = 2.0입니다. 이번 호라이즌의 몫은 다음과 같습니다.

이번 몫 = (전체 마감 − 지금) × 이번 가중치 ÷ (이번 것부터 끝까지의 가중치 합)

미리 표를 만들어 두지 않고 "지금"과 "남은 호라이즌"만으로 계산한다는 점이 핵심입니다. 모든 호라이즌이 제 몫만큼만 쓰면 이 식은 처음에 전체 예산을 가중치 비율로 나눈 것과 같은 결과를 냅니다. 어느 호라이즌이 늦게 끝나면, 늦어진 만큼을 남은 호라이즌들이 가중치 비율대로 나눠서 덜 받습니다. 마지막 호라이즌에서는 이번 가중치와 남은 가중치 합이 같으므로 마감이 정확히 전체 마감이 됩니다.

확장 ①: 새 블록은 어떤 값으로 출발하나

확장은 extend_schedule() 함수입니다. 워커 하나의 해(지금까지 들어온 블록들의 일정)와 새 블록 번호들을 받아, 새 블록까지 모두 놓인 해를 돌려줍니다. 해는 1장에서 본 ScheduledBlock의 목록이므로, 새 블록에도 일단 ScheduledBlock 하나를 만들어 줘야 합니다.

이 임시 값을 만드는 코드는 3장 6부에서 봤습니다(src/solver/optimize.rs:289). 입고 시각에는 추상 입고 시각(release보다 이르면 release)을, 출고 시각에는 거기에 P를 더한 값을, 베이에는 추상 베이를 넣고, 방향과 좌표는 0으로 채웁니다.

1장의 예시 블록 prelim_prob_1의 blocks[2](R = 30, P = 6, D = 36)로 보겠습니다. 추상 사전최적화가 이 블록에 베이 2, 입고 33일을 줬다고 가정하면(실제 값은 솔버를 실행해야 나옵니다) 만들어지는 값은 이렇습니다.

ScheduledBlock { block_id: 2, bay_id: 2, orient_idx: 0, x: 0, y: 0, entry_time: 33, exit_time: 39 }

이것은 실제 배치가 아닙니다. 좌표 (0, 0)과 방향 0은 채워 넣은 값일 뿐이고, 이 블록은 아직 일정에 들어가 있지 않습니다. 이 값은 탐욕 삽입 함수 insert_greedy에 "원래 값"(original)으로 넘어갑니다. 5장 5부에서 본 대로 그 함수가 여기서 읽는 것은 블록 번호와 출고 시각뿐입니다. 출고 시각에서 "원래 지연" = max(0, 39 − 36) = 3일을 계산하고, 지연이 3일 이하인 자리를 찾으면 그 방향의 탐색을 일찍 마무리합니다. 추상 베이 2는 읽지 않고, 베이는 이 블록의 선호 순서대로 모두 살펴봅니다.

정리하면 추상 입고 시각은 투입 순서를 정하고, 삽입에서는 "추상 일정만큼만 늦어도 충분히 좋은 자리"라는 기준 하나로만 남습니다.

insert_greedy가 original에서 읽는 필드는 src/solver/insert.rs:94(block_id)와 :108(exit_time)에서 확인했습니다. 살펴볼 베이의 순서는 호출할 때 넘기는 pre.bay_order_by_pref[block_id]입니다(optimize.rs:370).

확장 ②: 시도를 반복해 가장 좋은 것을 남긴다

새 블록 20개를 기존 일정 뒤에 그냥 덧붙이지 않습니다. 기존 블록 몇 개를 함께 빼서 새 블록과 섞어 다시 넣어 보고, 이것을 시간이 될 때까지 되풀이해 가장 좋은 결과 하나를 남깁니다. 이 한 번을 시도(trial)라고 부르겠습니다.

// src/solver/optimize.rs:303  extend_schedule() 의 시도 반복 (요약)
let mut best = None;
'trial: loop {
    if best.is_some() && 지금 >= 확장 마감 { break; }              // 완성된 해가 하나는 있어야 끝난다

    // ① 기존 블록 중 뺄 것을 고른다 (기존 일정이 비어 있으면 건너뛴다)
    removed_ids = choose_removed_blocks(base_schedule, sample_removed_count(…), …);

    // ② 뺀 블록을 제외한 일정, 베이별 작업량, 남은 블록들의 w₁Z₁ + w₃Z₃
    (schedule, loads, fixed_score13) = build_reconstruct_base(base_schedule, removed_ids);

    // ③ 뺀 블록 + 새 블록을 한 줄로 세운다
    order = removed_ids ++ added_block_ids;
    sort_default_reconstruct_order(&mut order, …);

    // ④ 순서대로 하나씩 탐욕 삽입
    for block_id in order {
        if best가 있고 fixed_score13 >= best.objective { continue 'trial; }    // 가지치기
        scheduled = insert_greedy(original_by_id[block_id], release_time, INF, &schedule, …)
                        else { continue 'trial; };                               // 삽입 실패
        loads[scheduled.bay_id] += workload;
        fixed_score13 += score13_block(scheduled);
        schedule.push(scheduled);
    }

    // ⑤ 전체 점수(w₂ 항 포함)를 매겨 지금까지의 최선과 비교
    candidate = make_optimize_state(schedule, w2);
    if best가 없거나 candidate.objective < best.objective { best = candidate; }
    if best.objective <= EPS { break; }                                          // 0점이면 더 볼 것이 없다
}
return best

Rust 읽는 법: 'trial:은 반복문에 붙인 이름입니다. 안쪽 for 안에서 continue 'trial을 만나면 안쪽 반복을 버리고 바깥 loop의 다음 회, 즉 다음 시도로 바로 넘어갑니다. ++는 두 목록을 이어 붙인다는 뜻으로 제가 쓴 표기입니다.

단계별로 정확히

  1. 뺄 블록 고르기. sample_removed_count가 7~13 사이의 수를 뽑습니다(remove_count의 range: [7, 13], power: 2.0. 작은 수가 더 자주 나오고, 분포 식으로 계산한 평균은 약 8.9입니다). 기존 블록이 그보다 적으면 있는 만큼만입니다. 어느 블록을 뺄지는 choose_removed_blocks가 정하고, 큰 재구성 이웃과 같은 함수입니다(7장).
  2. 남은 블록으로 바탕 만들기. build_reconstruct_base는 세 가지를 돌려줍니다. 뺀 블록을 제외한 일정, 베이별 작업량 합(loads, Z₂ 계산용), 남은 블록들의 w₁·지연 + w₃·선호 벌점 합입니다. 마지막 값이 코드의 fixed_score13이고, Z₁과 Z₃의 가중합이라 이름에 13이 붙습니다.
  3. 줄 세우기. 뺀 블록과 새 블록을 한 목록으로 합쳐 sort_default_reconstruct_order로 정렬합니다. 3장에서 본 그 함수입니다. 부피, 한계 시각의 급함, 여유의 빡빡함, 선호 차이, 난수를 가중합한 점수가 큰 순서이고, 가중치를 시도마다 새로 뽑습니다. 그래서 같은 블록들이라도 시도마다 넣는 순서가 다릅니다.
  4. 하나씩 삽입. 블록마다 insert_greedy를 부릅니다. 입고 시각의 범위는 그 블록의 release부터 INF(240)까지, 즉 상한이 없습니다. 삽입이 고른 자리를 일정에 추가하고 loads와 fixed_score13을 갱신합니다.
  5. 채점과 비교. 모두 넣었으면 make_optimize_state로 전체 점수를 매깁니다. 여기서 w₂·Z₂ 항이 더해집니다. 지금까지의 최선보다 작으면 교체합니다.

시도는 매번 같은 해에서 출발합니다.

①과 ②는 항상 이 워커가 들고 온 해(base_schedule)를 대상으로 합니다. 앞 시도의 결과를 이어받아 고쳐 나가는 것이 아니라, 같은 출발점에서 서로 다른 무작위 선택으로 여러 번 만들어 보고 가장 좋은 하나를 고르는 방식입니다. 고쳐 나가는 일은 그 뒤의 SA가 맡습니다.

배경: 난수 시드와 병렬 워커

프로그램의 난수는 시드라는 출발값에서 계산으로 만들어 내는 수열입니다. 시드가 같으면 수열도 같습니다. 그래서 워커 네 개가 같은 시드를 쓰면 넷이 똑같은 선택을 하게 되어 병렬로 돌리는 의미가 없습니다. 워커마다 시드를 다르게 주는 것이 "같은 알고리즘으로 서로 다른 탐색을 시키는" 가장 간단한 방법입니다.

SA에 넘어가는 것

  • 워커별 해 4개. 방금 확장한 결과입니다. 워커 r은 r번째 해에서 출발합니다.

왜 워커마다 해를 따로 들고 가나

호라이즌이 끝날 때 가장 좋은 해 하나를 골라 네 워커에게 복사해 줄 수도 있었을 것입니다. 이 해법은 그렇게 하지 않고, 처음부터 끝까지 네 개의 해를 나란히 키웁니다.

  • 구조가 다른 해 네 개가 유지됩니다. 2장에서 본 대로 빽빽한 일정은 앞쪽부터 굳습니다. 지금 점수가 가장 좋은 해의 앞쪽 구조가 나중에 들어올 블록들에게도 좋다는 보장은 없습니다. 기본 앵커와 시드가 다른 네 워커는 서로 다른 구석부터 채운 네 가지 구조를 끝까지 끌고 갑니다.
  • 그래도 크게 뒤처진 워커는 따라잡습니다. SA 동안 공유 최선보다 일정 기준 이상 나쁜 워커는 공유 최선을 내려받습니다. 그 기준과 주기는 7장에서 다룹니다.

보고서는 이를 "각 워커는 호라이즌을 넘어 자기 상태를 유지하고, 공유 최선을 갱신하며, 충분히 좋은 공유 해를 주기적으로 가져온다"고 적습니다. 워커 수를 1로 하거나 해를 하나로 합쳤을 때와의 비교 수치는 보고서에 없습니다.

3부 · w₂는 마지막 호라이즌에서만 켠다

호라이즌별 w₂를 정하는 함수

// src/solver/optimize.rs:257
fn horizon_w2(w2: f64, progress: f64, is_last: bool, power: Option<f64>) -> f64 {
    match power {
        Some(power) => w2 * progress.powf(power),       // 점진 도입: 진행률^power 만큼만
        None => if is_last { w2 } else { 0.0 },         // 기본: 마지막 호라이즌에서만
    }
}

progress는 누적 블록 수 ÷ 전체 블록 수이고, power는 파라미터 horizon_w2_power입니다. 이 파라미터는 src/params.rs:57에 선택 항목(Option<f64>)으로 정의되어 있지만 params/default.yaml에는 적혀 있지 않습니다. 그래서 값이 없는 상태(None)가 되고, 기본 동작은 2장에서 본 "마지막 호라이즌에서만 w₂"입니다.

w₂가 바뀌는 순간에 일어나는 일

  • w₂는 호라이즌의 맨 처음에 정해집니다. 그래서 마지막 호라이즌은 확장부터 공식 w₂를 씁니다. 새 블록을 넣을 때 베이별 Z₂ 증가분이 자리 비교에 들어가고, 시도의 최종 점수에도 w₂·Z₂가 더해집니다.
  • 앞 호라이즌의 점수는 버립니다. 워커가 들고 온 해에는 w₂ = 0으로 매긴 점수가 붙어 있지만, 확장은 그 해에서 일정만 꺼내 쓰고(state.schedule) 점수는 새 w₂로 다시 계산합니다. 기준이 다른 점수끼리 비교되는 일이 없습니다.
  • w₂ = 0인 동안에는 Z₂를 계산하지도 않습니다. 삽입 함수는 w₂가 0이면 Z₂ 계산을 통째로 건너뜁니다(src/solver/insert.rs:103).

optimize()의 마지막 줄은 최종 해를 문제의 원래 w₂로 다시 채점합니다.

두 방식 모두 마지막 호라이즌의 w₂는 원래 값과 같으므로(진행률이 1), 이 줄에서 점수가 달라지지는 않습니다. 반환하는 점수가 공식 목적 함수 값임을 호라이즌 설정과 무관하게 보장하는 줄입니다.

왜 마지막 호라이즌에서만 내보내나

중간 호라이즌의 해에는 아직 투입되지 않은 블록이 들어 있지 않습니다. 대회의 유효 조건은 모든 블록이 ENTRY와 EXIT를 한 번씩 갖는 것이므로(1장), 블록이 빠진 해는 내보내 봐야 무효입니다. 코드에서는 두 가지로 막혀 있습니다. 출력기를 SA에 넘기는 곳이 is_last.then_some(candidate_emitter)라서 마지막 호라이즌이 아니면 SA가 출력기를 받지 못하고, 간격의 초깃값이 무한대라서 configure() 전에는 강제가 아닌 출력이 통과하지 못합니다.

그 결과로 생기는 성질 하나.

솔버는 마지막 호라이즌의 확장이 끝날 때까지 아무것도 출력하지 않습니다. 명목 값으로 T = 300, 블록 250개라면 첫 후보는 약 239초 시점에 나옵니다. 그 전에 솔버가 죽으면 파이썬 쪽에는 후보가 하나도 없습니다.

간격을 두는 이유는 코드에 적혀 있지 않습니다. 후보 하나가 수십 KB이고 파이썬 쪽이 전부 파싱해야 하며, 출력하는 동안 다른 워커의 출력이 잠금에서 기다린다는 점을 생각하면 출력량을 묶어 두려는 것으로 보입니다. 이것은 제 해석입니다.

EXIT를 먼저 넣는다

// src/solver/output.rs:11  schedule_to_solution() (요약)
let mut operations: BTreeMap<i64, Vec<Operation>> = BTreeMap::new();   // 시각 → 그 시각의 작업 목록
for scheduled in schedule {                                            // 먼저 모든 블록의 EXIT
    operations.entry(scheduled.exit_time).or_default().push(EXIT …);
}
for scheduled in schedule {                                            // 그다음 모든 블록의 ENTRY
    operations.entry(scheduled.entry_time).or_default().push(ENTRY …);
}

일정을 두 번 훑습니다. 첫 번째에서 모든 블록의 EXIT를 각자의 출고 시각 목록에 넣고, 두 번째에서 ENTRY를 넣습니다. 그러면 어느 시각의 목록에서든 EXIT들이 ENTRY들보다 앞에 옵니다. 블록별로 "ENTRY, EXIT" 순서로 넣었다면 시각 30에 블록 2가 들어오고 블록 7이 나갈 때 ENTRY가 앞에 올 수 있습니다.

이 순서가 필요한 이유는 1장의 규칙입니다. 같은 시각의 작업은 EXIT를 모두 처리한 뒤 ENTRY를 처리하고, 출력에서도 EXIT가 앞에 적혀 있어야 합니다. 솔버는 "시각 30에 나가는 블록의 자리에 시각 30에 다른 블록이 들어온다"는 배치를 적극적으로 쓰므로 이 순서가 어긋나면 해가 무효가 됩니다.

같은 종류끼리의 순서(EXIT와 EXIT, ENTRY와 ENTRY)는 일정 목록에 들어 있던 순서 그대로이고 따로 맞추지 않습니다. 솔버가 같은 시각의 같은 종류 작업끼리 순서에 기대는 배치를 처음부터 만들지 않기 때문입니다(1장에서 본 "양 끝을 하루씩 안쪽으로" 잡는 처리, 5장). 보고서는 같은 시각의 작업 순서를 최적화하는 것도 시도했다가 버렸다고 적습니다.

검증은 무엇을 보나

check_feasibility_fast는 1장의 규칙을 다시 구현한 것입니다. 모든 블록의 ENTRY·EXIT가 한 번씩인지, 입고가 release 이후이고 체류가 작업 기간 이상인지, 블록이 베이 안에 있는지, 같은 시각에 EXIT가 ENTRY보다 앞에 적혔는지, 그리고 작업을 시각 순으로 재생하면서 들어오거나 나가는 블록이 그 순간 베이에 있는 다른 블록에 가려지지 않는지를 봅니다. 다각형 교차는 shapely로 계산하고, 바운딩 박스가 안 겹치는 쌍은 건너뛰고, 쌍별 결과를 기억해 두어 빠르게 만들었습니다. 검사 도중에도 수시로 시계를 봐서 T − 1을 넘으면 그만둡니다.

이 모든 것이 −1점 때문이다

대회 채점에서 무효한 해, 시간 초과, 비정상 종료는 그 문제에서 −1점입니다(1장). 유효한 해는 다른 팀보다 나빠도 그보다 높은 점수를 받으므로, 조금 나쁜 유효 해가 무효 해보다 항상 낫습니다. 4부의 장치들은 모두 이 비대칭에서 나옵니다.

5부 · 보고서와 코드를 나란히 놓고 보면

설명과 코드가 다른 부분

큰 줄기는 일치합니다. 고르게 나누는 방식, 확장의 5%·5초, 남은 시간으로 마감을 다시 계산하는 것, EXIT를 먼저 넣는 것은 보고서의 설명과 코드가 같습니다. 세부에서 어긋나거나 설명이 단순화된 곳은 다음과 같습니다.

항목보고서·발표 자료코드
호라이즌 안의 순서Algorithm 1은 확장(6~8행)을 먼저 하고 그 뒤에 w₂와 시간 배분(9~14행)을 정합니다.w₂와 마감을 먼저 계산하고 확장을 합니다. 확장도 그 w₂를 쓰고, 확장 시간은 이번 몫 안에서 떼어 냅니다(optimize.rs:437~454).
확장에서 다시 넣는 순서"무작위 순서로(in random order) 탐욕 재삽입"완전한 무작위가 아닙니다. 부피·한계 시각의 급함 등을 가중합한 점수 순이고, 가중치와 무작위 항을 시도마다 새로 뽑습니다(reconstruct.rs:643).
후보 해 출력"현재의 공유 최선을 탐색 중 주기적으로 내보낸다"마지막 호라이즌에서만, 공유 최선이 갱신된 순간에, 간격이 지났을 때만 내보냅니다. 여기에 강제 출력이 두 번 더 있습니다.
시간 배분의 Nh최종 발표 17쪽은 "호라이즌 h에 투입된 블록 수"라고 적습니다.누적 블록 수(horizon.end)입니다. 보고서 본문은 누적(cumulative)이라고 정확히 적고 있습니다.
w₂의 점진 도입시도했다가 버린 것horizon_w2_power라는 선택 항목으로 남아 있고, 기본 설정에서는 꺼져 있습니다.

이 장에서 확인하지 못한 것

  • 실행 결과 전부. 확장에서 시도가 몇 번 돌고 몇 번이 가지치기로 끊기는지, 후보가 실제로 몇 번 출력되는지, 사전계산과 검증에 몇 초가 걸리는지는 솔버를 돌려야 알 수 있습니다. 로그를 그려 주는 도구(tools/plot_horizon_score.py)는 저장소에 있습니다.
  • 호라이즌에 들어가는 실제 블록. 추상 사전최적화의 결과가 있어야 투입 순서가 나옵니다.
  • 파라미터 값의 근거. 호라이즌 크기 20, γ = 2.0, 확장 5%가 다른 값보다 얼마나 나은지는 보고서에 수치가 없습니다.
  • 검증 함수의 동등성. 파이썬 쪽 빠른 검증과 공식 검증기를 줄 단위로 대조하지 않았습니다.

이해 확인

블록 150개 문제는 호라이즌이 몇 개이고, 하나에 블록이 몇 개씩 들어가나요?

⌈150 / 20⌉ = 8개입니다. 150을 8로 고르게 나누므로 18개짜리 2개와 19개짜리 6개가 됩니다. 20개씩 7번 넣고 10개를 남기는 방식이 아닙니다. 20은 한 호라이즌 크기의 상한입니다.

어느 호라이즌의 SA가 예정보다 10초 늦게 끝났습니다. 전체 마감은 어떻게 되나요?

그대로입니다. 다음 호라이즌이 시작될 때 "전체 마감 − 지금"을 남은 호라이즌들의 가중치 비율로 다시 나누기 때문입니다. 늦어진 10초는 남은 호라이즌들이 가중치에 비례해 나눠서 덜 받습니다.

확장에 주어진 시간이 0초여도 새 블록은 일정에 들어가나요?

들어갑니다. 확장의 반복문은 "완성된 해가 하나 이상 있고 시간이 지났을 때"만 끝나므로 첫 시도는 반드시 끝까지 갑니다. 입고 시각에 상한이 없어서 삽입도 실패하지 않습니다. 다만 시도가 한 번뿐이라 여러 번 해 보고 고르는 효과는 없습니다.

확장의 한 시도에서 블록 4개만 넣고 그만두는 일이 있습니다. 왜 그래도 되나요?

이미 놓인 블록들의 w₁·지연 + w₃·선호 벌점 합이 지금까지의 최선 점수 이상이 되었기 때문입니다. 남은 블록을 넣으면 이 합은 늘거나 그대로이고 w₂·Z₂ 항도 0 이상이므로, 끝까지 가도 최선보다 좋아질 수 없습니다.

대회 제한이 300초인데 솔버가 멈추지 않으면 어떻게 되나요?

파이썬 쪽이 299초에 솔버를 강제 종료하고 그때까지 표준 출력에 나온 후보를 읽습니다. 검증할 시간은 남지 않았으므로 점수가 가장 좋은 후보를 검증 없이 돌려줍니다. 마지막 호라이즌의 확장이 끝나기 전이라 후보가 하나도 없었다면 예외가 나고, 그 문제는 −1점입니다.
