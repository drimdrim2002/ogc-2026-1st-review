SA와 이웃: 일정을 작게 자주, 가끔 크게 고친다

호라이즌마다 새 블록을 끼워 넣고 나면, 남은 시간은 전부 담금질 기법(simulated annealing, 이하 SA)에 씁니다. SA는 지금의 일정을 조금 바꾼 후보 일정을 만들고, 점수를 비교해 받아들일지 정하는 일을 마감까지 되풀이합니다. 온도와 수락 확률 같은 SA의 기본은 3장에서 추상 문제를 풀 때 봤습니다. 뼈대 코드는 그때와 같고, 이 장은 2단계에서 달라지는 것(온도를 정하는 방법, 워커 사이의 교환, 그리고 무엇보다 이웃)을 봅니다.

이 장은 그 한 번의 시도를 따라갑니다. 여기서 "시도"는 SA의 반복 한 번이고, 6장에서 확장의 한 회를 가리킨 "시도"와는 다른 것입니다. 먼저 SA가 다루는 데이터가 무엇인지 보고, 후보를 받아들이는 규칙(온도와 수락 임계값), 워커 4개의 병렬 실행, 후보를 만드는 네 가지 방법(이웃)을 차례로 봅니다. 네 이웃 중 큰 재구성이 이 해법의 세 번째 핵심 아이디어입니다.

1부 · SA가 다루는 데이터

상태: 일정 한 벌과 점수 하나

SA가 들고 다니는 해는 아래 구조체 하나입니다. 지금까지 투입된 블록마다 ScheduledBlock 한 줄이 있고, 그 일정의 목적 함수 값이 숫자 하나로 붙어 있습니다. 그 밖의 보조 자료구조(격자, 점유 지도, 블록 사이의 관계 그래프 등)는 상태에 없습니다.

이 장의 예시 배치에 대하여

이 기기에서는 솔버를 실행할 수 없어서, 솔버가 실제로 만든 일정을 보여 드리지 못합니다. 대신 prelim_prob_1의 블록 100개를 제가 단순한 규칙으로 직접 배치한 일정을 예시로 씁니다. 규칙은 이렇습니다. release가 빠른 순으로, 가장 선호하는 베이에, 바운딩 박스(블록의 모든 층을 감싸는 가장 작은 직사각형, 3장)가 가장 작은 방향으로, 다른 블록의 바운딩 박스와 겹치지 않는 가장 이른 날의 가장 왼쪽 자리에 놓습니다.

바운딩 박스끼리 겹치지 않으므로 규칙 A와 B를 어길 수 없습니다(공식 검증기는 이 기기에서 돌리지 못했습니다). 이 배치는 Z₁ = 21일(늦은 블록 6개), Z₃ = 0이고, w₂를 0으로 둔 점수가 21 × 21,622 = 454,062입니다. 솔버의 해는 블록을 훨씬 촘촘히 놓으므로 이보다 좋을 것입니다. 이 장에서 "예시 배치"라고 하면 이 일정입니다.

한 번의 시도

워커 하나가 마감까지 도는 반복문입니다. 기록용 코드를 빼면 이것이 전부입니다.

// src/solver/annealing.rs:389  run_worker() 의 반복문
loop {
    if stop { break }                                  // 다른 워커가 점수 0인 해를 찾았다
    elapsed = 지금 시각
    if elapsed >= deadline { break }                   // 시계는 매 반복마다 본다
    iterations += 1
    if iterations % 2000 == 0 { 공유 최선이 충분히 좋으면 가져온다 }

    T         = 온도(elapsed)
    threshold = current.objective − T · ln(u)          // u: 0 이상 1 미만의 균등 난수. 후보를 만들기 전에 뽑는다
    candidate = propose(current, threshold)            // 이웃 하나를 골라 후보 일정을 만든다

    if candidate 가 없음 { continue }                   // 이웃이 실패했다
    if candidate.objective > threshold { continue }    // 기각: 후보를 버린다
    current = candidate                                // 수락
    if candidate 가 이 워커의 최선보다 좋음 {
        personal_best = candidate
        공유 최선보다도 좋으면 공유 최선을 바꾼다
    }
}
  • 후보는 새 일정 전체입니다. 이웃 함수는 현재 일정을 고치지 않고 Vec<ScheduledBlock>을 새로 만들어 돌려줍니다. 기각되면 그 벡터를 버리면 끝이라, 되돌리는 코드가 없습니다.
  • 점수는 매번 처음부터 다시 계산합니다. 후보 일정이 나오면 score_schedule이 모든 블록을 한 번 훑어 Z₁, Z₂, Z₃를 다시 구합니다. 바뀐 블록만 따져 차이를 구하는 방식(차분 계산)이 아닙니다. 블록 수백 개에 대한 덧셈이라 싸고, 시간이 드는 쪽은 블록이 들어갈 자리를 찾는 일(5장의 한 행 훑기)입니다.
  • 실패한 시도도 한 번으로 셉니다. 이웃이 후보를 못 만들어도 iterations는 올라갑니다.

propose는 src/solver/optimize.rs:151, 후보의 점수를 계산하는 make_optimize_state는 optimize.rs:42, score_schedule은 src/solver/objective.rs:12입니다. SA 뼈대(Annealer)는 문제를 모르는 일반 코드이고, 문제에 특화된 부분은 AnnealingDelegate 트레이트(다른 언어의 인터페이스에 해당)의 구현체가 맡습니다. 3장의 추상 사전최적화도 같은 Annealer에 다른 구현체를 끼워 씁니다.

2부 · 받아들이는 규칙

수락 임계값을 먼저 뽑는다

3장에서 수락 규칙을 "새 값 ≤ 지금 값 − T × ln(u)"라는 꼴로 적고 오른쪽을 수락 임계값이라고 불렀습니다. 그렇게 쓰는 이유가 여기서 나옵니다. 흔한 SA는 후보를 만든 뒤에 난수를 뽑아 받아들일지 정합니다. 이 코드는 순서가 반대입니다. 후보를 만들기 전에 "이번에는 점수가 얼마 이하면 받겠다"는 값을 먼저 정합니다. 이 값이 수락 임계값(accept_threshold)입니다.

임계값 = 현재 점수 − T · ln(u)   (u는 0 이상 1 미만의 균등 난수, T는 온도)
// src/solver/annealing.rs:125
pub(crate) fn acceptance_threshold(current_score: f64, temperature: f64, rng: &mut impl Random) -> f64 {
    current_score - temperature * rng.next_f64().ln()
}
// annealing.rs:435  수락 판정은 비교 한 번
let accepted_candidate = candidate_score <= accept_threshold;
  • ln(u)는 0 이하이므로 임계값은 항상 현재 점수 이상입니다. 그래서 점수가 좋아지거나 같은 후보는 무조건 수락됩니다.
  • 현재보다 Δ만큼 나쁜 후보가 수락되려면 Δ ≤ −T·ln(u), 즉 u ≤ e^(−Δ/T)여야 합니다. 그럴 확률은 e^(−Δ/T)입니다. 흔한 SA의 수락 규칙과 확률이 같고, 난수를 뽑는 시점만 다릅니다.
  • 먼저 뽑는 이유는 임계값을 이웃에게 넘겨줄 수 있기 때문입니다. 이웃은 후보를 만드는 도중에 "이대로 가면 임계값을 넘는다"는 것을 알면 바로 그만둘 수 있습니다. 실제로 이 값을 쓰는 이웃은 큰 재구성 하나입니다(4부).

온도는 "블록 하나당 평균 점수"에서 나온다

온도의 단위는 목적 함수의 단위와 같아야 합니다. 그런데 w₁이 문제에 따라 333에서 21,622까지 달라서 온도를 고정된 숫자로 둘 수 없습니다. 이 코드는 SA를 시작할 때의 점수를 블록 수로 나눈 값을 기준으로 삼습니다.

  • 초기 점수는 그 호라이즌의 확장(6장)이 끝난 직후, 워커들의 일정 중 가장 좋은 것의 점수입니다. 블록 수는 그때까지 투입된 블록 수입니다.
  • 온도 일정은 호라이즌마다 새로 계산됩니다. 호라이즌 안에서는 점수가 좋아져도 T₀와 T₁이 바뀌지 않고, 시간만 보고 내려갑니다.
  • 워커 넷이 같은 온도 일정을 씁니다.

이 온도가 실제로 어느 정도인지 prelim_prob_1(w₁ = 21,622, w₃ = 150)의 숫자로 보겠습니다. 초기 점수는 솔버를 실행해야 알 수 있어서, 아래 표의 s는 가정한 값입니다. 첫 줄은 앞의 예시 배치의 점수를 초기 점수로 가정한 것이고, 나머지 두 줄은 지연이 더 많은 상황을 가정한 것입니다.

4,541 (지연 0.21일분)908 → 915 × 10⁻¹¹ → 사실상 019% → 7 × 10⁻⁸
21,622 (지연 1일분)4,324 → 4320.67% → 사실상 071% → 3.1%

화살표 왼쪽은 SA를 시작할 때, 오른쪽은 호라이즌 마감 때입니다. 블록당 평균 점수가 지연 a일분이면 T₀는 지연 0.2a일분이므로, 하루 늦어지는 후보의 수락 확률은 시작할 때 e^(−5/a), 끝날 때 e^(−50/a)입니다.

표에서 읽을 수 있는 것은 온도가 문제의 혼잡도에 따라 저절로 달라진다는 점입니다. 지연이 거의 없는 일정에서는 블록을 하루 늦추는 후보를 처음부터 받지 않고, 선호 몇 점을 주고받는 정도만 허용합니다. 지연이 많은 일정에서는 초반에 하루 이틀 늦추는 후보도 자주 받다가, 끝으로 갈수록 받지 않게 됩니다.

초기 점수와 블록 수를 넘기는 곳은 src/solver/optimize.rs:85입니다. 표의 확률은 e^(−Δ/T)에 숫자를 넣어 계산했습니다.

언제 끝나나

  • 마감 시각. 매 반복의 첫머리에서 경과 시간을 읽고, 호라이즌 마감을 넘었으면 끝냅니다. 몇 번에 한 번만 시계를 보는 식의 절약은 하지 않습니다. 반복 횟수의 상한도 없습니다.
  • 점수 0. 어느 워커든 점수가 0(정확히는 10⁻⁹ 이하)인 일정을 받아들이면 공용 깃발 stop을 세우고, 다른 워커들도 다음 반복에서 멈춥니다. 더 좋아질 수 없기 때문입니다.

3부 · 후보를 만드는 방법: 작은 이웃 세 가지

어느 이웃을 쓸지는 주사위로 정한다

배경: 차량 경로 문제의 이웃에 빗대면

Shift, Rotate, Move는 "하나를 빼서 다른 자리에 넣는" relocate 계열의 작은 이웃입니다. 고객 하나를 경로의 다른 위치로 옮기듯 블록 하나의 자리를 다시 정합니다. 4부의 큰 재구성은 여러 개를 한꺼번에 빼고 다시 넣는 ruin-and-recreate, 즉 큰 이웃 탐색입니다(2장).

다른 점이 하나 있습니다. 경로 문제의 relocate는 보통 옮길 곳을 무작위로 하나 찍어 평가하지만, 여기의 작은 이웃은 블록을 고른 뒤 정해진 범위(행 몇 개, 방향 전부, 또는 모든 베이)를 훑어 그중 가장 좋은 자리를 냅니다. 블록이 겹치지 않는 자리 자체가 드물어서, 무작위로 찍으면 대부분 들어가지 않기 때문입니다.

이웃(neighborhood)은 현재 일정에서 후보 일정을 만드는 방법을 가리키는 말입니다. 네 가지가 있고, 시도마다 아래 가중치에 비례하는 확률로 하나를 고릅니다.

Shift: 방향과 베이는 그대로, 구석 쪽으로 다시 놓는다

  1. 일정에서 블록 하나를 무작위로 골라 뺍니다.
  2. 기준점의 y를 원래 y + dy로 바꿔 가며 한 행 훑기를 합니다. dy_range: [-5, 0]이므로 dy는 −5부터 0까지 여섯 값입니다. 앵커가 위쪽(왼쪽 위, 오른쪽 위)이면 부호를 뒤집어 0부터 +5까지입니다. 즉 앵커 쪽으로만 움직입니다.
  3. 한 행 훑기의 입고 시각 범위는 release 이후 전부입니다. 지금보다 늦은 시각도 후보가 됩니다.
  4. 여섯 행에서 나온 모든 후보 중 하나를 고릅니다. 지연이 작은 것, 같으면 입고가 이른 것, 그래도 같으면 바운딩 박스가 앵커 쪽 구석에 가까운 것입니다. 원래와 좌표·시각이 완전히 같은 후보는 빼고 고릅니다.

Rotate: 방향을 바꾸되 같은 높이에 놓아 본다

방향을 바꾸면 블록이 기준점을 중심으로 돕니다. 기준점은 층 0의 첫 꼭짓점일 뿐 블록의 한가운데가 아니므로, 같은 (x, y)에 다른 방향을 놓으면 블록이 엉뚱한 곳을 차지합니다. 그래서 코드는 "방향 a에서 방향 b로 바꿀 때 기준점 행을 얼마나 옮겨야 블록이 원래 높이에 오는가"를 미리 계산해 둡니다. 실제 값을 보겠습니다.

  2. 위 목록의 방향마다, 기준점의 y를 원래 y + dy + ddy로 두고 한 행 훑기를 합니다. dy_range: [-2, 2]이므로 ddy는 −2부터 +2까지 다섯 값입니다. 방향이 8개인 블록이면 7 × 5 = 35개 행입니다.

2장에서 본 잠김을 작은 이웃의 눈으로 다시 보면 이렇습니다. 빽빽한 일정에서 블록 하나를 빼면 생기는 틈은 그 블록의 모양과 기간에 꼭 맞는 틈입니다. 다시 넣을 곳이 사실상 원래 자리뿐입니다. 서로 맞물린 블록 셋의 배열을 바꾸려면 셋이 함께 움직여야 하는데, 작은 이웃은 한 번에 하나만 옮깁니다. 중간 단계가 매번 유효하고 수락될 만해야 하므로, 구조가 다른 채우기로 건너가지 못합니다.

배경: 큰 이웃 탐색에서 "무엇을 뺄까"

부수고 다시 짓는 탐색의 성패는 무엇을 부수느냐에 달려 있습니다. 차량 경로 문제의 큰 이웃 탐색에서 흔히 쓰는 제거 방식은 셋입니다. 아무거나 빼는 무작위 제거, 지금 비용을 가장 많이 내는 것을 빼는 최악 제거(worst removal), 서로 가까운 것들을 함께 빼는 연관 제거(related removal, Shaw removal)입니다. 연관 제거가 중요한 이유는, 서로 상관없는 것들을 빼면 각자 원래 자리로 돌아갈 뿐이기 때문입니다.

이 해법의 큰 재구성에도 세 가지가 다 들어 있습니다. 시드를 고르는 방식(무작위, 나쁨)이 앞의 둘이고, 시드 주변을 거리 d로 함께 빼는 것이 연관 제거입니다. 다만 방식마다 따로 연산자를 두고 성적에 따라 고르는 적응형(ALNS)이 아니라, 한 번의 재구성 안에서 고정 비율로 섞습니다.

큰 재구성은 가까이 있는 블록 여러 개를 한꺼번에 빼고, 다른 순서로 다시 넣는 이웃입니다. 한 번의 시도 안에서 구조를 바꾸므로 중간 상태를 SA에 보일 필요가 없습니다. 2장에서 본 대로 발표 자료의 실험에서는 이 이웃을 뺐을 때 목적 함수 값이 10.5% 나빠졌습니다.

② 시드 고르기

k개를 아무 데서나 흩어 뽑으면 서로 관계없는 블록 k개를 각각 다시 넣는 것과 같아서, 작은 이웃을 k번 한 것과 다르지 않습니다. 그래서 먼저 중심이 될 블록 몇 개를 고르고, 각 중심의 주변을 함께 뺍니다. 이 중심 블록이 시드(seed)입니다.

시드마다 묶음 크기를 정한다

시드 하나가 자기를 포함해 몇 개를 빼는지를 remove_blocks_per_seed: { range: [1, 4], power: 1.0 }에서 뽑습니다. power가 1이라 1~4가 같은 확률입니다. 합이 k가 될 때까지 뽑으므로 시드 수가 따라 정해집니다. k = 9라면 [2, 3, 1, 3]처럼 됩니다. 평균 시드 수는 k = 7일 때 3.2개, k = 13일 때 5.6개입니다(같은 규칙을 20만 번 돌려 센 값).

시드를 고르는 방식 세 가지

시드마다 아래 셋 중 하나를 가중치 1 : 1 : 2로 뽑습니다(remove_seed_method_weights).

badness (나쁨)25%나쁨 점수가 높은 순으로 k개w₁ × 지연 + w₃ × 선호 벌점 + (작업량이 가장 무거운 베이에 있으면 w₂)

기준 시드와 따라가는 시드

시드들을 완전히 따로 뽑으면 일정의 여기저기가 조금씩 뜯깁니다. 코드는 앞의 한두 개만 자유롭게 뽑고, 나머지는 그것과 입고 시각이 가까운 블록 중에서 뽑습니다.

  1. 간격 값을 3, 4, 5 중에서 같은 확률로 뽑습니다(remove_entry_base_interval_weights: [0, 0, 1, 1, 1]. 앞의 두 0은 1과 2가 나오지 않게 합니다).
  2. 1 + (시드 수 − 1) ÷ 간격(나머지 버림)개가 기준 시드입니다. 시드가 4개이고 간격이 3이면 2개입니다. 기준 시드는 위의 방식대로 자유롭게 뽑습니다.
  3. 나머지 시드는 기준 시드 하나를 무작위로 짝지은 뒤, 자기 방식의 후보를 그 기준 시드와의 입고 시각 차이가 작은 순으로 줄 세워 앞의 5개만 남기고(remove_entry_seed_candidate_count: 5), 그중 하나를 균등하게 고릅니다.

이때 베이는 따지지 않습니다. 오히려 입고 시각 차이가 같으면 기준 시드와 다른 베이의 블록이 앞에 옵니다. 그래서 큰 재구성 한 번이 "비슷한 시기에 들어오는 블록들"을 여러 베이에 걸쳐 뜯을 수 있습니다. 같은 시기의 블록끼리 베이를 맞바꾸는 재배치를 가능하게 하려는 것으로 보이지만, 이 의도는 보고서에 없어 제 추정입니다. 보고서는 "첫 시드 이후의 시드는 기존 시드와 입고 시각이 가까운 쪽으로 치우치게 한다"고만 적었습니다.

③ 시드 주변 블록을 함께 뺀다

시드마다, 같은 베이에 있는 다른 블록들을 시드와의 거리 순으로 줄 세우고 가까운 것부터 (묶음 크기 − 1)개를 함께 뺍니다.

d(i, s) = λx · |Δx|^p + λy · |Δy|^p + λt · |Δt|^p

Δx와 Δy는 두 블록의 바운딩 박스 중심 사이의 차이, Δt는 입고 시각의 차이입니다. 네 숫자는 큰 재구성을 시도할 때마다 아래 범위에서 새로 뽑습니다.

값범위뜻
λx[0.1, 4.0]x 방향 거리의 무게. 범위가 40배라, 어떤 시도는 x를 거의 무시하고 어떤 시도는 x를 가장 중시한다
λy[0.001, 0.002]y 방향 거리의 무게. 다른 둘의 수백분의 1 이하

λy가 유독 작습니다. 범위의 가운데 값(λx = 2.05, λy = 0.0015, λt = 1.0, p = 3)으로 계산하면, 입고가 5일 차이 나는 것과 같은 거리가 되려면 x는 3.9, y는 44만큼 떨어져야 합니다. 베이의 세로는 15~29이므로 y가 44만큼 떨어지는 일은 없습니다. 즉 y는 사실상 무시되고, x와 입고 시각이 가까운 블록이 이웃입니다.

이유는 보고서에 없습니다. 제 추정은 베이의 모양입니다. 학습 데이터에서 블록의 바운딩 박스는 세로의 중앙값이 문제에 따라 8~12인데 베이의 세로는 15~29입니다. 같은 x 위치에는 블록이 세로로 두 개쯤밖에 못 섭니다. x와 시기가 같은 블록은 y가 어떻든 서로 자리를 다투는 사이이므로, 함께 빼야 그 세로 띠 전체를 새로 짤 수 있습니다.

시드의 베이에 블록이 모자라 k개를 못 채우면, 나쁨 점수 상위 k개 중에서 무작위 순으로 채웁니다.

        &cur, &loads, insert_params, &pre.bay_order_by_pref[old.block_id], w2, anchor, rng)?;
    loads[scheduled.bay_id] += problem.blocks[scheduled.block_id].workload as f64;
    fixed_score13 += score13_block(problem, pre, scheduled);      // 방금 넣은 블록의 벌점을 확정 합에 더한다
    cur.push(scheduled);
}
허용 지연 = ⌊(임계값 − 확정 합) ÷ w₁⌋   ·   입고 시각 상한 = 납기 + 허용 지연 − 작업 기간

이 가지치기가 옳은 이유는 이렇습니다. 최종 점수는 확정 합보다 작을 수 없습니다. 아직 안 넣은 블록의 벌점과 w₂ × Z₂는 0 이상이기 때문입니다. 지금 넣는 블록의 지연이 허용 지연을 넘으면 그것만으로 확정 합이 임계값을 넘고, 그 후보는 어차피 기각됩니다. 그러니 그렇게 늦은 입고 시각은 찾아볼 필요가 없습니다. 탐욕 삽입은 더 좁은 시간 범위만 보고, 그 안에 자리가 없으면 바로 포기합니다.

예시의 숫자로 따라가 봅니다. 온도를 908, 난수 u를 0.5로 가정하면 임계값은 454,062 + 908 × 0.693 = 454,691입니다.

차례그때의 확정 합허용 지연입고 시각 상한
블록 68 (납기 54, P 9)324,330⌊(454,691 − 324,330) ÷ 21,622⌋ = ⌊6.03⌋ = 6일54 + 6 − 9 = 51일
블록 89 (납기 48, P 11)410,818 (68이 지연 4일로 들어갔다고 가정)⌊(454,691 − 410,818) ÷ 21,622⌋ = ⌊2.03⌋ = 2일48 + 2 − 11 = 39일

블록 68은 지금 51일에 들어가 6일 늦고 있습니다. 상한이 정확히 51일이므로 "지금보다 더 늦어지는 자리는 보지 않는다"가 됩니다. 68이 이틀 앞당겨져 지연 4일로 들어가면 86,488이 확정 합에 더해지고, 남은 예산 43,873으로는 다음 블록이 최대 2일까지만 늦을 수 있습니다. 앞 블록이 예산을 아끼면 뒤 블록의 선택지가 넓어지고, 앞에서 다 쓰면 뒤에서는 지연 없는 자리만 허용됩니다. 표의 "68이 지연 4일로 들어갔다"는 가정이고, 실제 삽입은 솔버를 돌려야 알 수 있습니다.

  • 앵커는 블록마다 새로 뽑습니다(80%는 워커의 기본 앵커).
  • 블록의 원래 배치가 original로 넘어가지만, 삽입이 거기서 읽는 것은 원래 지연뿐입니다(5장). "지금만큼은 덜 늦는 자리"가 행 탐색을 일찍 끝내는 기준이 되고, 베이와 방향은 모두 다시 봅니다.
  • 확정 합에는 Z₂가 없습니다. w₂ × Z₂를 포함한 최종 점수는 다 넣은 뒤 SA가 계산해 임계값과 비교합니다.

실패하면 어떻게 되나

큰 재구성은 아래 어느 경우든 None을 돌려주고 그 시도를 끝냅니다.

  • 시드를 뽑으려는데 그 방식의 후보가 모두 이미 시드로 쓰였을 때
  • 블록을 넣기 전에 확정 합이 이미 임계값을 넘었을 때
  • 탐욕 삽입이 허용 범위 안에서 자리를 찾지 못했을 때(입고 시각 상한이 release보다 이른 경우 포함)

실패했을 때 따로 하는 일은 없습니다. 일부만 넣은 결과를 살리지도 않고, 순서를 바꿔 다시 해 보지도 않습니다. 작업을 현재 일정의 복사본에서 했으므로 복사본을 버리면 현재 일정은 처음 그대로입니다. SA는 다음 반복으로 넘어가 이웃을 새로 뽑습니다. 실패가 싸다는 점이 이 설계의 요점입니다. 가망 없는 시도를 일찍 끊고 그 시간에 다른 시도를 합니다.

모든 블록이 들어가면 그것이 후보 일정입니다. 뺀 블록이 모두 다시 들어가 있으므로 블록 수는 그대로입니다.

큰 재구성의 실패 비율이나 수락 비율은 실행해야 알 수 있어 확인하지 못했습니다. 솔버를 local 기능을 켜고 빌드하면 워커가 끝날 때 이웃별 선택·성공·개선·수락 횟수와 걸린 시간을 로그로 남깁니다(src/solver/annealing.rs:156).

저자가 시도했다가 버린 것

기술 보고서의 "Key Ideas that Failed" 절에는 SA와 이웃에 관한 시도가 일곱 가지 나옵니다. 다시 넣는 순서를 여러 개 싸게 탐색하려던 빔 서치 재구성, 최선 상태로 돌아가 크게 흔드는 재가열과 킥, 이미 간 상태로 되돌아가지 않게 막는 해시 타부, 출고 시각을 맞바꾸는 시간 변경, 같은 날의 입출고 순서 최적화, 관측한 점수 차이로 온도를 정하는 적응형 온도, 크레인 길을 막는 블록을 직접 골라 빼는 이웃입니다. 이유가 따로 적힌 것은 빔 서치뿐입니다. 삽입 결과를 재사용하는 것보다 다양한 배치 상태를 탐색하는 쪽이 더 중요했다는 것입니다. 항목별 설명과 git 기록에 남은 흔적은 8장 4부에 표로 정리되어 있습니다.

같은 절에는 목적 함수의 세 항을 단계별로 나눠 최적화하는 방식과 w₂를 서서히 켜는 방식도 버린 것으로 적혀 있습니다(6장의 영역입니다). 보고서의 향후 계획에는 가림 관계를 제거 블록 선택에 더 직접 쓰는 것, 수락률에 기반한 온도 조절을 다시 검토하는 것, 워커가 온도대나 이웃 구성을 나눠 맡는 병렬 방식이 올라 있습니다. 지금의 병렬 방식은 네 워커가 온도와 이웃 확률이 모두 같고 기본 앵커만 다릅니다.

보고서의 설명과 코드가 다른 곳

Shift. 보고서는 "가까운 이동량 하나를 뽑는다"고 적었습니다. 코드는 뽑지 않고 dy 여섯 값을 모두 훑어 가장 좋은 후보를 고릅니다. x는 가까운 범위가 아니라 행 전체입니다.

Rotate. 보고서는 "바운딩 박스 IoU로 미리 계산한, 기하학적으로 비슷한 방향으로 바꾼다"고 적었습니다. 코드는 다른 방향을 전부 시도합니다. IoU는 방향을 걸러 내는 데가 아니라 방향마다 y 이동량 dy를 정하는 데 쓰입니다.

시드. 발표 자료는 "시드 블록 여러 개를 무작위로 고른다"고 줄여 적었습니다. 코드는 나쁨, 유동성, 무작위를 1 : 1 : 2로 섞고, 보고서 본문도 그렇게 적었습니다.

거리. 보고서의 식은 블록의 좌표 x, y를 씁니다. 코드에서 그 좌표는 기준점이 아니라 바운딩 박스의 중심입니다.

이해 확인

온도가 T일 때, 현재보다 2.3 T만큼 나쁜 후보가 수락될 확률은 얼마인가요? 임계값을 먼저 뽑는 방식이라 달라지는 것이 있나요?

e^(−2.3) ≈ 10%입니다. 임계값을 먼저 뽑아도 확률은 같습니다. 달라지는 것은 이웃이 후보를 만들기 전에 그 값을 알 수 있다는 점이고, 큰 재구성이 이를 이용해 받아들여질 수 없는 삽입을 미리 잘라 냅니다.

Shift로 만든 후보의 점수가 현재와 달라진다면, 목적 함수의 어느 항 때문인가요?

Z₁뿐입니다. Shift는 베이를 바꾸지 않으므로 Z₂(베이별 작업량)와 Z₃(베이 선호)는 그대로이고, 옮긴 블록의 지연만 달라질 수 있습니다. 그래서 점수 변화는 0이거나 w₁의 배수입니다. 0인 경우는 항상 수락됩니다.

prelim_prob_1에서 어떤 워커의 현재 점수가 공유 최선보다 지연 2일분만큼 나쁩니다. 2,000번째 반복에서 이 워커는 공유 최선을 가져오나요?

가져오지 않습니다. 지연 2일분은 2 × 21,622 = 43,244인데, 이 문제의 exchange_threshold는 min(216,220, 75,000) = 75,000입니다. 차이가 75,000을 넘어야 갈아탑니다. 이 워커는 자기 일정을 계속 고칩니다.

큰 재구성에서 블록 9개 중 세 번째를 넣으려는데 자리가 없습니다. 이미 넣은 두 개는 어떻게 되나요?

버려집니다. 시도 전체가 None이 되고, SA의 현재 일정은 아홉 블록이 원래 자리에 있는 그대로입니다. 큰 재구성은 현재 일정의 복사본에서 작업하므로 되돌릴 것이 없습니다. 다음 반복에서 이웃과 난수를 새로 뽑아 다른 시도를 합니다.
