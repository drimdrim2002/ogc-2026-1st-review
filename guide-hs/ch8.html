3부 · 버린 시도와 개발 방식

시도했다가 버린 아이디어 아홉 가지

1등 해법이 처음부터 깔끔했던 것은 아닙니다. 저자는 수많은 아이디어를 코드에 넣어 실험하고, 문제 전체에서 뚜렷한 이득이 없으면 과감히 지웠습니다(전체 407개 커밋 중 49개가 되돌리기 커밋입니다).

버린 시도무엇을 노렸나버린 이유
빔 서치 재구성삽입 결과를 여러 후보가 재사용해 재삽입 순서를 싸게 탐색재사용보다 다양한 배치 상태를 탐색하는 것이 더 중요했다
항목별 다단계 최적화지연, 선호, 작업량 불균형을 단계를 나눠 따로 최적화표준 탐색보다 뚜렷한 이점이 없었다
재가열과 킥, 해시 타부정체되면 온도를 올리거나 이미 간 상태로 못 돌아가게 막음롤링 호라이즌 도입 뒤 효과가 없어 제거
w₂ 점진 도입마지막 호라이즌에서 한 번에 켜는 대신 서서히 올림부담만 늘고 일관된 개선 없음
같은 날 작업 순서·출고 교환같은 날 입출고 순서나 출고 시각 맞바꾸기까지 탐색복잡도만 늘고 개선 없음
적응형 온도, 가림 블록 제거점수 차이로 온도 자동 조절 / 크레인 길을 막는 블록 직접 제거유망해 보였으나 문제 전반에서 안정적으로 맞추기 어려움

눈여겨볼 점은 "탐색을 똑똑하게 만드는 복잡한 장치보다, 빠르고 단순하게 다양한 상태를 많이 시도하는 쪽이 이겼다"는 것입니다. 빔 서치를 버리고 큰 재구성에서 가중치를 매번 무작위로 뽑은 선택이 이를 보여 줍니다.

파라미터 파일과 자동 측정 고리

알고리즘의 동작을 좌우하는 숫자 68개는 코드에 박아 두지 않고 params/default.yaml 파일 하나에 모아 두었습니다. 이렇게 해 두면 "파라미터를 바꾼다 → 문제 묶음 전체에 돌린다(클라우드에서 20개 작업으로 병렬 실행) → 점수를 비교한다"는 과정을 자동으로 반복할 수 있습니다.

버전끼리 비교할 때는 목적 함수 값을 그대로 더하지 않고 상대 점수(문제마다 "최선 값 ÷ 내 값"을 구해 더한 값)를 썼습니다. 문제마다 점수가 수만 배씩 달라서, 그냥 더하면 큰 문제 몇 개만 보게 되기 때문입니다. 또 해를 2D·3D로 눈으로 볼 수 있는 시각화 도구를 네 가지나 만들어, 해가 어디서 꼬이는지 직접 보며 아이디어를 얻었습니다.

4부 · 다른 문제로 가져갈 다섯 가지 교훈

조선소 블록을 걷어 내고 남는 것

이 해법에서 조선소 블록에 특화된 부분을 덜어 내면, 다른 "채우기 + 일정" 최적화 문제에도 그대로 쓸 수 있는 다섯 가지 설계 원칙이 남습니다.

가져갈 원칙이 해법에서의 모습언제 통하나장
1. 단순화한 문제로 큰 방향을 먼저 잡는다모양을 숫자 하나(넓이)로 줄여 베이와 입고 시각을 먼저 풀고, 결과는 투입 순서에만 쓴다어려운 기하 제약을 빼도 자원 경쟁의 큰 그림이 남을 때2, 3
2. 끝자리에서 한 번씩 고치며 키운다20개씩 추가할 때마다 들어온 블록 전체를 다시 최적화한다(롤링 호라이즌). 전체 균형 항(Z₂)은 마지막에만 켠다한꺼번에 넣으면 앞쪽이 굳어 움직이지 못할 때2, 6
3. 공간과 시간을 한 번의 훑기로 푼다상대 위치별 충돌 격자를 미리 만들고, x를 훑으며 금지 시각 구간을 건너뛰어 자리와 시각을 한 번에 찾는다두 물체 사이의 충돌이 상대 위치만으로 정해질 때4, 5
4. 여러 개를 한꺼번에 뜯어 고친다가까운 블록 7~13개를 함께 빼고 매번 다른 가중치 순서로 다시 넣는다(큰 재구성). 임계값으로 가망 없는 시도를 빨리 버린다하나씩 옮겨서는 서로 맞물린 구조를 못 바꿀 때7
5. 유효성 재검증과 시간 안전장치후보 해를 여러 번 내보내고 다른 방법으로 다시 검증한다. 호라이즌마다 남은 시간을 다시 나눈다무효한 해의 벌칙이 크고 제한 시간이 정해져 있을 때1, 6

다섯 가지는 서로 맞물려 있습니다. 1번의 순서가 있어야 2번의 롤링 호라이즌이 잘 돌고, 3번의 빠른 삽입이 있어야 4번의 큰 재구성을 많이 시도할 수 있으며, 5번의 안전장치가 있어야 탐색을 과감하게 밀어붙일 수 있습니다.

더 알고 싶다면

  • 저자가 밝힌 다음 개선 과제. 현재는 1단계(추상 사전최적화)가 2단계로 순서를 넘겨주기만 하는 한 방향입니다. 저자는 2단계의 실제 배치 결과를 다시 1단계로 되먹여 추상 모델의 정확도를 높이는 방법, 호라이즌 크기를 문제 크기에 맞춰 자동 조절하는 방법, 그리고 워커마다 온도대를 다르게 두는 병렬화를 향후 과제로 꼽았습니다.
  • AI 코딩 에이전트 활용. 저자는 알고리즘 설계와 검증은 직접 하되, 구현과 보고서 초안에는 AI 코딩 에이전트를 보조로 썼습니다. 저장소의 AGENTS.md에는 "코드를 작게 유지하고, 파라미터는 파일로 빼고, 성능 측정은 따로 한다"는 규칙이 적혀 있습니다. 그 결과 전체 Rust 솔버는 약 6,000줄로 간결하게 유지되었습니다.

이해 확인

40문제 합계에서 전체 해법이 제거 실험보다 약 10% 좋았습니다. 모든 문제에서 10%씩 앞선 것인가요?

아니요. 합계는 값이 큰 6문제가 70%를 차지합니다. 문제별로 보면 40문제 중 31문제에서 전체 해법이 1위였고, 9문제에서는 사전최적화나 롤링 호라이즌을 뺀 쪽이 더 좋았습니다. 특히 어려운 큰 문제 10개에서는 한 번도 지지 않았습니다.

롤링 호라이즌을 빼면 작업량 불균형(Z₂)이 20% 좋아지는데, 왜 전체 점수는 나빠지나요?

Z₂가 전체 점수에서 차지하는 비중이 0.1%뿐이기 때문입니다. Z₂에서 약 10만을 아꼈지만, 지연(Z₁)과 선호 벌점(Z₃)에서 약 4,800만을 잃어 전체적으로는 크게 손해였습니다.

버전을 비교할 때 목적 함수 값을 그냥 더하지 않고 "상대 점수"를 쓴 이유는 무엇인가요?

문제마다 목적 함수 값이 수만 배씩 다르기 때문입니다. 그냥 더하면 값이 큰 몇 문제의 결과만 반영되지만, 문제마다 "최선 값 ÷ 내 값"으로 바꾸어 더하면 모든 문제가 같은 무게를 갖게 됩니다.

본선 P1에서는 12.5% 앞섰고 P2에서는 1.1% 앞섰습니다. 대회 등수 점수에는 어떤 차이가 있나요?

차이가 없습니다. 등수 점수는 "나보다 좋은 팀 수"로만 정해지므로 둘 다 39점입니다. 반대로 무효한 해를 내면 −1점이 되어 한 문제에서 40점을 잃으므로, 모든 문제에서 유효하고 고른 성적을 내는 것이 중요합니다.
